## 维度一：🔒 安全审计（权重 35%）

> 检查项目是否存在安全漏洞——硬编码密钥、云开发配置、数据注入、权限控制等。
> **详细检查标准和报告格式见** `Skill.md` →「security-audit」章节。

### 执行流程

1. **硬编码敏感信息**：用 Grep 搜索 `password`、`secret`、`apiKey`、`token`、`AppSecret`、`access_key`、`env:` 等关键词，不区分大小写
2. **云开发安全配置**：检查 `app.js` 中云环境 ID 是否硬编码、数据库权限配置、云函数是否有身份校验
3. **数据注入风险**：搜索数据写入操作，确认是否过滤了用户输入
4. **敏感数据泄露**：检查 `console.log` 中是否打印了用户 openid/手机号等隐私数据
5. **输入验证**：检查金额、备注、预约信息相关的校验逻辑
6. **权限控制**：检查所有 admin 页面是否在 onLoad 中校验了 isAdmin
7. **其它隐患**：搜索硬编码 URL、未处理异常、`any` 类型滥用等

### 严重度标准

| 级别 | 含义 | 标记 |
|:----:|------|:----:|
| 🔴 严重 | 可直接导致数据泄露或用户隐私暴露 | 必须立即修复 |
| 🟡 中等 | 在特定条件下可被利用 | 建议本周修复 |
| 🟢 轻微 | 不良实践，不直接导致安全事件 | 下个迭代改进 |
| ⚪ 通过 | 该项检查无问题 | — |

### 小程序专属安全检查（必查！）

#### 云数据库权限
确认各集合的权限设置合理：
| 集合 | 建议权限 | 风险 |
|------|----------|------|
| nail_styles | 所有用户可读，仅管理员可写 | 如果"所有用户可写"→ 任何人都能改款式数据 |
| bookings | 用户可读自己的，管理员可读写全部 | 如果"所有用户可读"→ 顾客隐私泄露 |
| admin_users | 仅管理员可读 | 如果"所有用户可读"→ 管理员 openid 暴露 |
| points | 用户可读自己的 | 如果"所有用户可写"→ 用户可刷积分 |

#### 管理员权限校验
检查所有 admin 页面的 `onLoad`：
```js
// ✅ 安全做法
onLoad() {
  if (!app.globalData.isAdmin) {
    wx.showToast({ title: '无权限访问', icon: 'none' });
    wx.navigateBack();
    return;
  }
}
```

#### app.json 权限声明
检查是否合理使用了微信权限：
- `scope.userLocation` 是否必要（门店地图需要）
- 是否有未使用但声明了的权限

## 维度二：💬 注释检查（权重 30%）

> 检查注释覆盖率、准确性、小白友好度。
> **详细检查标准和报告格式见** `Skill.md` →「comments-check」章节。

### 三维度标准

#### 2.1 注释覆盖率（目标 ≥ 30%）

统计方法：
- 注释行 = `//` 开头、`/* */` 包裹、`/** */` JSDoc
- 代码行 = 包含实际逻辑/声明的行
- 不计算：空行、只有花括号的行、纯 import/require 语句

重点检查：
- 每个页面的 `Page({})` 中的自定义方法必须有注释
- `utils/cloud.js` 每个导出函数必须有 JSDoc
- 复杂逻辑必须有行内解释
- 每个 JS 文件顶部必须有模块说明

#### 2.2 注释准确性

逐注释检查：读注释 → 理解描述的行为 → 看代码实际做什么 → 判断是否一致。

#### 2.3 小白友好度

- 技术术语必须有白话解释
- 复杂逻辑必须有生活比喻
- 数字和阈值必须有来源说明

### 注释质量要求

| 要求 | 说明 |
|------|------|
| 🇨🇳 中文注释 | 所有注释必须用中文 |
| 📝 JSDoc 必写 | 每个导出函数必须有 |
| 🎯 解释"为什么" | 不是翻译代码，是解释意图 |
| 🧩 复杂逻辑拆解 | 逐步解释 |
| 🧠 小白能懂 | 用生活比喻替代技术黑话 |

## 维度三：📏 代码规范（权重 35%）

> 检查代码风格、错误处理、最佳实践等。

### 3.1 错误处理

| # | 检查项 | 搜索/检查方法 |
|---|--------|--------------|
| 1 | 云函数调用是否处理失败 | 检查 `.catch()` 或 try-catch |
| 2 | 空 catch 块 | 搜索 `catch\s*\([^)]*\)\s*\{\s*\}` |
| 3 | 用户可见的错误提示 | 检查 `wx.showToast` 的 title 是否为中文 |
| 4 | 数据库操作的错误处理 | 检查 `cloud.js` 中是否有 fallback |

### 3.2 小程序最佳实践

| # | 检查项 | 方法 |
|---|--------|------|
| 1 | 页面 onShow/onLoad 重复数据加载 | 检查是否在 onShow 中不合理地重复请求数据 |
| 2 | setData 调用是否过大 | 检查是否一次性 setData 了过多数据（>1MB 会卡） |
| 3 | 全局状态管理 | 检查页面是否有不必要的重复全局变量读取 |
| 4 | 页面栈深度 | 检查页面跳转链路是否有超过 10 层的风险 |
| 5 | 图片懒加载 | 检查长列表中的图片是否用了 `lazy-load` |

### 3.3 代码整洁度

| # | 检查项 | 方法 |
|---|--------|------|
| 1 | 过长的函数（> 50 行） | 逐文件扫描 |
| 2 | console.log 残留 | 搜索 `console.log(` |
| 3 | 硬编码的魔法数字 | 检查数字字面量，标记无注释说明的 |
| 4 | 未使用的变量/导入 | 人工检查 |
| 5 | 缩进和格式一致性 | 2空格缩进，WXML属性不换行 |

### 3.4 WXML 规范

| # | 检查项 | 方法 |
|---|--------|------|
| 1 | 属性值是否换行 | 搜索 WXML 中跨行的 `class="..."` |
| 2 | wx:for 是否有 wx:key | 检查每个 `wx:for` |
| 3 | 条件渲染 | `wx:if` vs `hidden` 使用是否正确 |
| 4 | 事件绑定 | `bindtap` vs `catchtap` 场景是否合理 |

### 评分公式

```
总分 = 安全审计得分×0.35 + 注释检查得分×0.30 + 代码规范得分×0.35

各维度得分：
  安全审计 = max(100 - 严重数×25 - 中等数×10 - 轻微数×3, 0)
  注释检查 = 覆盖率得分×0.4 + 准确性得分×0.35 + 友好度得分×0.25
    覆盖率得分 = min(注释率/30% × 100, 100)
    准确性得分 = max(100 - 严重数×30 - 中等数×10, 0)
    友好度得分 = max(100 - 不友好项数×15, 0)
  代码规范 = max(100 - 严重数×20 - 中等数×8 - 轻微数×2, 0)
```

## 执行注意事项

1. **先扫描再报告**：不要一边扫描一边报告，先把三个维度全部查完，再统一输出
2. **每条问题必须有代码行号**：用地毯式 Grep 搜索后，Read 打开文件确认上下文，引用精确行号
3. **防误报**：区分"测试 mock 数据"和"生产代码"、"变量声明"和"硬编码赋值"、"import 路径"和"URL"
4. **中文优先**：报告、建议、错误描述全部用中文
5. **报告完成后主动询问**：是否要我针对 🔴 严重问题生成修复代码？

## 完成标记：写入质量检查结果文件

> **必须执行！** 在所有模式的质量报告输出完毕后，必须将结果写入 JSON 标记文件。

### 操作步骤

在质量报告输出完毕后，使用 Write 工具创建/覆盖项目根目录下的 `.claude/quality-result.json`。

### JSON 格式

```json
{
  "passed": true,
  "totalScore": 85,
  "securityScore": 90,
  "commentScore": 80,
  "standardScore": 85,
  "threshold": 75,
  "timestamp": "2026-08-12T12:00:00.000Z"
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `passed` | boolean | 总分 ≥ 75 为 true，否则为 false |
| `totalScore` | number | 质量综合评分（0-100） |
| `securityScore` | number | 安全审计维度得分 |
| `commentScore` | number | 注释检查维度得分 |
| `standardScore` | number | 代码规范维度得分 |
| `threshold` | number | 通过阈值，固定为 **75** |
| `timestamp` | string | 当前时间，ISO 8601 格式 |

### 通过标准

| 分数段 | 等级 | 是否通过 |
|--------|:----:|:--------:|
| ≥ 90 | 🟢 优秀 | ✅ 通过 |
| 75-89 | 🟡 良好 | ✅ 通过 |
| 60-74 | 🟠 需改进 | ❌ 不通过 |
| < 60 | 🔴 不合格 | ❌ 不通过 |

### 判定规则

- `passed` = (totalScore >= threshold)，即总分 ≥ 75
- 三种维度得分必须取自报告中的实际评分，不能编造
- 单维度模式时，未检查的维度得分记为 100（满分），避免拉低总分
- 该文件是 gitcommit-agent 和 PreToolUse hook 判断是否允许提交的依据
